## 1. Overview

Production (`credpay-prod`) is watched in four ways. Prometheus and Grafana are always on;
Slack, Dynatrace and Azure OpenAI switch on when their secrets are in Key Vault.

```
┌──────────────────────────────── AKS cluster ─────────────────────────────────────┐
│                                                                                    │
│  credpay-prod pods                                                                 │
│  user-service  payment-service  keycloak  ai-service  portals                      │
│     │  /metrics                         │                                          │
│     │                                   │ OneAgent code modules (injected)         │
│     ▼                                   ▼                                          │
│  ┌────────────── monitoring ───────────────┐    ┌──────── dynatrace ───────────┐   │
│  │ Prometheus ──rules──► Alertmanager ─────┼──┐ │ Operator, OneAgent per node, │   │
│  │    │                                    │  │ │ ActiveGate                   │   │
│  │    └──► Grafana (dashboards)            │  │ └──────────────┬───────────────┘   │
│  │ node-exporter, kube-state-metrics       │  │                │                   │
│  └─────────────────────────────────────────┘  │                │                   │
│                                                │                │                   │
│  ai-service ◄── Prometheus, Alertmanager, Kubernetes API, Dynatrace problems       │
│      │                                         │                │                   │
└──────┼─────────────────────────────────────────┼────────────────┼──────────────────┘
       ▼                                         ▼                ▼
  Azure OpenAI                             Slack webhook      Dynatrace SaaS
  (briefing + Ask CredAI)                  #credpay-alerts    (Davis AI problems)
       │
       ▼
  admin portal → Monitoring page, Ask CredAI
```

| Question | Answered by | Where you see it |
| --- | --- | --- |
| How much traffic, how many errors, how slow? | Prometheus | Grafana, admin portal Monitoring |
| Is something wrong right now? | Prometheus alert rules → Alertmanager | Slack, Grafana, admin portal Monitoring |
| Which line of code / which call is slow, and why? | Dynatrace OneAgent + Davis AI | Dynatrace, admin portal Monitoring |
| What does it all mean, in plain English? | ai-service + Azure OpenAI | admin portal: Generate briefing, Ask CredAI |

## 2. Components

| Component | Namespace | Installed from | Configuration |
| --- | --- | --- | --- |
| Prometheus, Alertmanager, Grafana, node-exporter, kube-state-metrics, Prometheus Operator | `monitoring` | Helm chart `prometheus-community/kube-prometheus-stack` **92.13.1** | [`kube-prometheus-stack-values.yaml`](../k8s/platform/monitoring/kube-prometheus-stack-values.yaml) + a file generated by [`scripts/cd/monitoring-values.sh`](../scripts/cd/monitoring-values.sh) |
| ServiceMonitors, alert rules, Grafana dashboard | `credpay-prod` | the CredPay chart | [`charts/credpay/templates/monitoring.yaml`](../charts/credpay/templates/monitoring.yaml), [`charts/credpay/dashboards/`](../charts/credpay/dashboards) |
| Dynatrace Operator, OneAgent, ActiveGate | `dynatrace` | Helm chart `oci://public.ecr.aws/dynatrace/dynatrace-operator` **1.11.1** | [`../dynatrace/dynakube.yaml`](../k8s/platform/dynatrace/dynakube.yaml) |
| ai-service (AIOps, Ask CredAI) | `credpay-prod` | the CredPay chart (`aiops.enabled: true` in prod) | [`charts/credpay/templates/ai-service.yaml`](../charts/credpay/templates/ai-service.yaml) |

The chart versions are pinned in [`pipelines/credpay-cd.yml`](../pipelines/credpay-cd.yml)
(`kubePrometheusStackChartVersion`, `dynatraceOperatorChartVersion`).

**Only prod is monitored by the app's rules and dashboards.** `monitoring.enabled` is `true`
only in `values-prod.yaml`. dev and qa still show up in the general Kubernetes dashboards
(CPU, memory, pods), but they have no ServiceMonitors, alerts or Slack messages - a broken
dev should not wake anyone up.

## 3. How the pipeline installs it

Two stages of `credpay-cd` are involved.

**Platform stage** (once per cluster, every run - `helm upgrade --install` is idempotent),
in [`scripts/cd/install-observability.sh`](../scripts/cd/install-observability.sh):

```
1. read-optional-secrets.sh     reads Slack / Dynatrace / OpenAI from Key Vault
                                 → SLACK_ENABLED, DYNATRACE_ENABLED, OPENAI_ENABLED = true|false
2. Secrets in "monitoring"      grafana-admin        (always, from grafana-admin-password)
                                 alertmanager-slack   (if SLACK_ENABLED)
3. monitoring-values.sh         generates the values that change per cluster:
                                 Grafana host grafana.<domain>, certificate issuer,
                                 and - if Slack is on - the Slack receiver and message format
4. helm upgrade --install monitoring prometheus-community/kube-prometheus-stack
       -f kube-prometheus-stack-values.yaml     (fixed settings, in git)
       -f <generated values>                    (per cluster, never in git)
5. if DYNATRACE_ENABLED:
     helm upgrade --install dynatrace-operator …        (+ CRDs)
     Secret "dynakube" in "dynatrace"  (apiToken, dataIngestToken)
     kubectl apply dynakube.yaml  (ENVIRONMENT_URL replaced with dynatrace-url)
```

**Deploy prod stage**, in [`scripts/cd/deploy-app.sh`](../scripts/cd/deploy-app.sh):

```
Secret credpay-aiops            OpenAI endpoint/key/deployment, Dynatrace URL + problems token
helm upgrade credpay …          creates the ServiceMonitors, PrometheusRule, dashboard ConfigMap
                                 and ai-service; with Dynatrace on, adds the
                                 metrics.dynatrace.com/* annotations to the pods
```

No secret is ever written into a values file or a Helm release: the Slack webhook, the
Dynatrace tokens and the OpenAI key go straight from Key Vault into Kubernetes Secrets.

## 4. Prometheus - collecting metrics

**How Prometheus finds the services.** The Prometheus Operator watches for `ServiceMonitor`
objects. The values file sets `serviceMonitorSelectorNilUsesHelmValues: false` (and the same
for rules and pod monitors), so Prometheus picks them up **from every namespace**, not only
from its own Helm release. The CredPay chart creates one ServiceMonitor per service:

| Service | Scraped endpoint | Main metrics |
| --- | --- | --- |
| user-service (Spring Boot) | `http:/actuator/prometheus` | `http_server_requests_seconds_*` (uri, status), JVM |
| payment-service (FastAPI) | `http:/metrics` | `http_requests_total` (handler, status `2xx/4xx/5xx`), `http_request_duration_seconds_*` |
| keycloak | `management:/metrics` (port 9000) | `http_server_requests_seconds_*`, JVM |
| ai-service (FastAPI) | `http:/metrics` | same as payment-service |

Every 30 seconds. Each series gets two extra labels, `environment` and `service`, so
queries and alerts never depend on pod names.

From the stack itself: **kube-state-metrics** (desired vs available replicas, restarts,
pod phase), **node-exporter** (node CPU, memory, disk), **kubelet/cAdvisor** (CPU and memory
per container).

**Storage**: 7 days or 8 GB, whichever comes first, on a 10 Gi Azure disk (PVC).

**Turned off on purpose**: scraping of the control plane (controller manager, scheduler,
etcd, kube-proxy). AKS runs the control plane for us, so it cannot be scraped - leaving it on
would only produce false alerts.

**Recording rules** pre-compute the two numbers everything else uses:

| Rule | Meaning |
| --- | --- |
| `credpay:http_error_ratio:rate5m` | share of requests answered 5xx, per service (health checks and scrapes left out) |
| `credpay:http_latency_p95:rate5m` | 95th percentile response time in seconds, per service |

## 5. Alert rules

`PrometheusRule credpay-alerts` in [`charts/credpay/templates/monitoring.yaml`](../charts/credpay/templates/monitoring.yaml).
Every alert has the labels `severity`, `team: credpay` and `environment`, a summary, a
description and a `runbook_url` pointing at [09-OBSERVABILITY-ALERTS-RUNBOOKS.md](09-OBSERVABILITY-ALERTS-RUNBOOKS.md#alerts-and-runbooks).

| Alert | Fires when | For | Severity |
| --- | --- | --- | --- |
| `CredpayServiceDown` | Prometheus cannot scrape user-service, payment-service or keycloak (`up == 0`) | 2 min | critical |
| `CredpayDeploymentUnavailable` | a deployment has fewer available replicas than desired | 10 min | warning |
| `CredpayPodCrashLooping` | a container restarted more than 3 times in 15 minutes | at once | critical |
| `CredpayHighErrorRate` | more than 5% of a service's requests return 5xx | 5 min | critical |
| `CredpayHighLatency` | 95th percentile response time above 1 second | 10 min | warning |
| `CredpayPaymentErrors` | more than 3 failed (5xx) payments in 10 minutes | at once | critical |
| `CredpayContainerMemoryHigh` | a container uses more than 90% of its memory limit | 15 min | warning |

"For" means the condition must stay true that long before the alert fires - short blips
do not page anyone.

## 6. Alertmanager and Slack

Prometheus evaluates the rules and sends firing alerts to Alertmanager, which decides
**who gets told**. The routing (base in the values file, Slack part generated):

```
every alert
 ├─ alertname = Watchdog      → "null"   (heartbeat of the stack, always firing - never notify)
 ├─ team = credpay            → slack    (all CredPay alerts, and their resolution)
 └─ anything else             → "null"   (the stack's own Kubernetes alerts: visible, not sent)

group_by:        alertname, namespace, service   (one message per problem, not per pod)
group_wait:      30s    wait for related alerts before the first message
group_interval:  5m     wait before sending updates for the same group
repeat_interval: 4h     remind while it keeps firing
inhibit:         a critical alert mutes the warnings of the same service
```

**Slack** is a plain **Incoming Webhook** - nothing is installed in the cluster. The URL is
in the Secret `alertmanager-slack`, mounted into the Alertmanager pod and read with
`api_url_file`, so it never appears in a config file or log. The message format (title,
colour, runbook link, link to the Grafana dashboard) is in `monitoring-values.sh`:

```
🚨 FIRING: CredpayHighLatency (credpay-prod)          red = critical, orange = warning
WARNING user-service is slow in prod
95% of user-service requests take up to 1.4s (threshold 1s).
Runbook
                    … later …
✅ RESOLVED: CredpayHighLatency (credpay-prod)         green
```

Without Slack, the alerts are still visible in Alertmanager, Grafana and the admin portal.

## 7. Grafana

| | |
| --- | --- |
| URL | `https://grafana.<domain>` - Ingress through Traefik, certificate from cert-manager (`grafana-tls`) |
| Login | user `admin`, password = Key Vault `grafana-admin-password` (Secret `grafana-admin`); sign-up is off |
| Data source | Prometheus (and Alertmanager), set up by the chart |
| Dashboards | **CREDPAY → CREDPAY - Service Overview** (ours), plus the stack's *Kubernetes / …* and *Node Exporter / …* dashboards |
| Storage | none (`persistence.enabled: false`) - everything is provisioned from code |

**How our dashboard gets in:** the CredPay chart packs `charts/credpay/dashboards/*.json`
into a ConfigMap labelled `grafana_dashboard: "1"` with the annotation
`grafana_folder: CREDPAY`. Grafana's **sidecar** watches all namespaces for that label and
loads the dashboard into the folder. To change the dashboard, edit the JSON in git -
changes made in the Grafana UI are lost when the pod restarts.

## 8. Dynatrace

Configured in [`../dynatrace/dynakube.yaml`](../k8s/platform/dynatrace/dynakube.yaml):

| Part | What it does |
| --- | --- |
| **Dynatrace Operator** | manages everything below from the `DynaKube` object |
| **OneAgent** (`cloudNativeFullStack`) | one pod per node (host, process and network monitoring) **and** code modules injected into new pods of `credpay-prod` only - this gives traces down to the method and SQL call |
| **ActiveGate** | one pod, on the `user` node pool: monitors the Kubernetes API (workloads, events) and routes the agents' traffic to Dynatrace |
| **Metadata enrichment** | adds namespace and workload names to prod's data |
| **Prometheus metrics** | the pipeline adds `metrics.dynatrace.com/scrape` annotations to prod pods, so Dynatrace ingests the same metrics as Prometheus |

The operator connects with two tokens from the Secret `dynakube` (operator token, data
ingest token). ai-service uses a third, **read-only** token (`problems.read`) to show
Dynatrace's open problems on the admin portal.

Injection happens **when a pod is created**: pods that started before Dynatrace was
installed need a restart (`kubectl rollout restart deploy -n credpay-prod`).

## 9. AIOps and Ask CredAI

**ai-service** (`credpay-prod`, admin-only) collects one picture of prod from Prometheus,
Alertmanager, the Kubernetes API (read-only, own namespace) and Dynatrace problems, then:

| Feature | Admin portal | Needs Azure OpenAI? |
| --- | --- | --- |
| Overview: status, services, alerts, problems, restarts | **Monitoring** page (refreshes every 30 s) | no |
| Briefing: main problem, likely cause, impact, next steps | Monitoring → **Generate briefing** | no - rule-based without it, AI-written with it |
| Chat with follow-up questions | **Ask CredAI** | yes |

Only operational facts (health, alerts, metrics, events) and the admin's question are sent
to Azure OpenAI - no customer data and no logs. Details: [09-OBSERVABILITY-ALERTS-RUNBOOKS.md](09-OBSERVABILITY-ALERTS-RUNBOOKS.md#aiops).

## 10. Switching integrations on and off

| Integration | Key Vault secrets | Then |
| --- | --- | --- |
| Slack | `slack-webhook-url` | run `credpay-cd` |
| Dynatrace | `dynatrace-url` (the `…live.dynatrace.com` address), `dynatrace-api-token`, `dynatrace-data-ingest-token`, `dynatrace-problems-token` | run `credpay-cd`, approve prod |
| Azure OpenAI | `azure-openai-endpoint` (ends in `/openai/v1`), `azure-openai-key`, `azure-openai-deployment` | run `credpay-cd`, approve prod |

Delete the secrets and run the pipeline again to switch one off. The *Read optional
integrations* step of every run prints which ones are on. Restarting pods is **not** enough
after changing a secret: the pods read the values the last pipeline run copied into the
cluster.

## 11. Commands

```bash
# What is running
kubectl get pods -n monitoring
kubectl get pods -n dynatrace ; kubectl get dynakube -n dynatrace
kubectl get servicemonitor,prometheusrule -n credpay-prod

# Prometheus UI (targets, rules, queries) → http://localhost:9090
kubectl port-forward -n monitoring svc/monitoring-prometheus 9090:9090
#   Status → Targets: every credpay-prod service should be UP
#   Alerts: the CredPay rules and their state

# Alertmanager UI (alerts, silences) → http://localhost:9093
kubectl port-forward -n monitoring svc/monitoring-alertmanager 9093:9093

# The Alertmanager configuration actually in use (no secrets in it)
kubectl get secret -n monitoring alertmanager-monitoring-alertmanager-generated \
  -o jsonpath='{.data.alertmanager\.yaml\.gz}' | base64 -d | gunzip

# Logs
kubectl logs -n monitoring sts/alertmanager-monitoring-alertmanager -c alertmanager --tail=50
kubectl logs -n dynatrace deploy/dynatrace-operator --tail=50
kubectl logs -n credpay-prod deploy/ai-service --tail=50
```
