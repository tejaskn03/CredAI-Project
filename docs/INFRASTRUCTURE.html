The big picture

One region, one cluster, three environments

CredPay runs on one AKS cluster in Canada Central. Dev, qa and prod are namespaces in that cluster and share one PostgreSQL server, where each environment has its own databases. This keeps the cost classroom-friendly while still showing how real teams separate environments and promote one build to production.

How a Helm deploy protects you

helm upgrade --install credpay charts/credpay -n credpay-prod \
  -f values-prod.yaml --set-string domain=... --set-string userService.image=... \
  --atomic --wait --timeout 15m --history-max 10
--wait

Done only when every pod passes its readiness probe.

--atomic

Not Ready in 15 minutes? Helm rolls back automatically.

--history-max 10

Keeps 10 releases for helm rollback credpay <rev>.

checksum/config

A config change restarts the pods that read it.

Secrets never pass through Helm. The pipeline copies them from Key Vault into Kubernetes Secrets first. The chart refers to them by name only, so they never appear in values or in Helm's release history.

Reliability

Keep working correctly, and recover without a person
2 healthy pods
→
one crashes; traffic goes to the other
→
Kubernetes starts a replacement

Health probes

Readiness: no traffic until ready. Liveness: restart if stuck. Startup probes give user-service and keycloak 3 and 5 minutes to boot.

Self-healing

Crashed pods are recreated; pods on a dead node move to healthy nodes.

Rolling updates

New pods must be Ready before old ones stop: no downtime with 2+ replicas.

Automatic rollback

helm --atomic returns to the previous release if the new one never becomes Ready.

Requests and limits

Every container declares CPU and memory, so no service can starve the others.

Autoscaling

HPA: 2–4 pods for the prod APIs. Cluster autoscaler: 2–5 system and 0–4 user nodes.

Gates

SonarQube and Trivy in CI, 10 smoke tests after every deploy, approvals before qa and prod.

Detect and alert

7 Prometheus alert rules → Slack. Dynatrace and the AIOps page help find the root cause.

Backups

PostgreSQL: 7 days of point-in-time restore. State in Azure Storage, images in ACR.

The 10 smoke tests run through the real ingress. They check that HTTP redirects to HTTPS, both portals are served and point at Keycloak, Keycloak publishes the right issuer, payment-service answers, and the user, admin and payment APIs refuse calls without a login (401). One failure stops the promotion.

High availability and redundancy

An honest look at every layer

High availability means users can still use the app when a part fails. Redundancy is how you get it: more than one copy of each part, so there is no single point of failure.

Redundant Single, recovers quickly Single point of failure
Load balancer + IPAzure Standard LBmanagedRedundant inside Azure.
Nodes2–5 system, 0–4 userredundantPods move to the other node. Not spread across availability zones.
Prod APIs2–4 pods + PDBredundantThe other pod serves; a node drain never removes both.
Prod portals2 pods + PDBredundantThe other pod serves.
Control planerun by Microsoftfree tierRunning pods keep serving; only deploys and scaling pause.
Traefik1 podsingleAll traffic stops until it restarts (seconds). Easy to raise to 2.
Keycloak1 podsingleNew logins fail for a few minutes; signed-in users keep working. More replicas need its cache cluster.
dev / qa1 pod eachby designShort outage on restart; fine for test environments.
PostgreSQL1 server, no standbySPOFAll environments stop until Azure recovers it. Data is safe in backups.
RegionCanada Central onlySPOFA region outage takes everything down; rebuild elsewhere with Terraform + CD.

Why this is fine for the course: each step up (zones, an HA database, a second region) roughly doubles part of the bill. This setup shows the mechanisms: replicas, PDBs, HPA, the autoscaler, probes and rollback. Section 11 shows what a bank would add.

Parts in a chain multiply

99.9%cluster× 99.9%database= ≈ 99.8%~1.5 h / month
  • AKS Free tier (used here): no financially backed SLA for the control plane. Standard tier: 99.9%, or 99.95% with availability zones.
  • PostgreSQL Flexible Server without HA: 99.9%. With zone-redundant HA: 99.99%.
  • Redundancy at every layer (zones, HA database, more replicas) is how companies push the total above 99.9%.
